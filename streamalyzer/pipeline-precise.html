New approach for computing delay (and other properties) inspired by Streaming String Transducers

Context: The previous model of a network device was too permissive, which made the analysis more complex in general. In the new model, a device step can only branch on:

  • its visible state — the part of its state that is exposed to the control logic (e.g., whether a queue is empty or not, but not the specific length or the packets it contains); and
  • the incoming packets at this step — whether one arrives, plus whatever of it the control is allowed to read.

It cannot branch on the data it has stored: the packets it is buffering, its internal counters and timers, and any other latent register state are invisible to the branch decision. Stored contents may only be forwarded, buffered, released, or rewritten by fixed assignments — never inspected to choose what to do. This is exactly the discipline of a Streaming String Transducer (the control depends only on the input and a finite state, while the unbounded registers are transformed blindly), and it is what makes the visible behaviour a finite automaton and the delay analysis tractable.

The pipeline at a glance

The pipeline reuses one engine: ③ Reachability and the reachability step inside ⑤ (both green) are the same algorithm — REACH in the step-3 and step-5 pseudocode. Step ⑤ only adds a cost variable to the WACS and reads off its maximum at the exits.

1 · The device: a cyclic gated shaper

We use one example device throughout, the same device at every step: a cyclic gated shaper. A gate alternates between closed and open every P ticks. Arriving packets are appended to a FIFO buffer of capacity C; while the gate is open two packets leave per tick, while it is closed nothing leaves and the queue fills. We want to know: how long can a packet wait before it is forwarded?

The device has two levels of state — the full concrete state, and the visible part the step is allowed to branch on:

  • concrete state {closed, open} × {0, …, P−1} × (buffer of ≤ C packets): the gate, a hidden countdown timer t ∈ {0, …, P−1}, and the queued packets, whose length is q ∈ {0, …, C}. Each tick the timer does t → t−1 and, at 0, flips the gate and reloads to P−1. The two integers t (timer) and q (queue length) are the variables the rest of the document tracks.
  • visible state {closed, open} × {empty, nonempty}: the gate, plus a coarse queue view — here just whether the queue is empty. Four values, the nodes of step 2.

The step branches only on those four visible values; it never reads the timer or the buffered packets — it can only advance the timer, enqueue, and dequeue.

The step function

One tick, in pseudocode. The only branch is on the visible state — the gate bit and whether the queue is empty; the state update is the same every tick.

step(input, gate, queueEmpty):     # gate and queueEmpty are the visible state

    # outputs — the only branch, on the visible state
    if gate is open and not queueEmpty:
        out1, out2 := popOrNothing(), popOrNothing()   # up to 2 packets leave this tick
    else:
        out1, out2 := none, none                       # gate closed, or queue empty

    # state update — the same every tick, no branch:
    advance the timer:  t := t − 1;  on wrap (t = 0) flip the gate and reload t := P − 1
    enqueue(input)                     # append to the buffer (dropped if the buffer is full)

The queueEmpty test is not strictly necessary — popOrNothing already yields nothing on an empty queue, so the device behaves the same without it. We read it as visible state anyway: it splits each gate phase into an empty and a nonempty case, which gives the cleaner four-node automaton of step 2.

import Network.CoreSST.Storage.DualCounter
import Network.CoreSST.Storage.BoundedFIFO

/-!
Cyclic gated shaper over the fused `DualCounter` phase storage.

Behaviorally the same device as `cyclicGatedShaper`, distilled to its decision content:

* the gate bit and its phase timer live in one storage component (`DualCounter`) whose
  visible view is *only the gate bit* — the timer, including whether this is the last tick
  of the phase, is hidden;
* the FIFO is used through `popIfNonempty`, whose storage semantics already make popping an
  empty queue a no-op, so the device does not consult the queue view at all.

The `step` function therefore branches on a single visible bit (is the gate open?) and
emits the same update list on every tick (`advance` the phase, `push` the input).

The queue's device-facing view `LenUpTo K` is a pure *representation dial* with no effect
on behavior or on the analysis result: `K = 0` gives the minimal two-node visible graph
(timer and queue length fully symbolic); `K = 2` exposes queue length {0, 1, 2+} as visible
structure (six nodes), which reads more like a classical automaton.
-/

namespace CoreSST.Devices

namespace CyclicGatedShaperDual

/-- Fused gate-bit/timer phase storage: visible gate, hidden `Bool × Fin P`. -/
abbrev phaseStorage (P : Nat) : StorageSignature :=
  DualCounter.storageSignature (P - 1)

/-- Bounded FIFO whose `LenUpTo K` view the step never reads (`K` is the dial only). -/
abbrev queueStorage (C K : Nat) : StorageSignature :=
  Signatures.BQueue.storageSignature C K

/-- Product storage for the fused phase and the bounded FIFO. -/
abbrev storageSignature (C P K : Nat) : StorageSignature :=
  Product.storageSignature (phaseStorage P) (queueStorage C K)

/-- Pop the FIFO head if the queue is nonempty; a no-op on the empty queue. -/
def popIfNonempty {C P K : Nat} : (storageSignature C P K).Output :=
  Sum.inr Signatures.BQueue.Output.pop

/-- Advance the fused phase counter (tick; toggle gate and reset on wrap). -/
def advancePhase {C P K : Nat} {α : Type _} : (storageSignature C P K).Update α :=
  Product.leftUpdate (S := phaseStorage P) (T := queueStorage C K)
    DualCounter.advance

/-- Push one current input packet into the FIFO. -/
def pushInput {C P K : Nat} {α : Type _} (packet : Option α) :
    (storageSignature C P K).Update α :=
  Product.rightUpdate (S := phaseStorage P) (T := queueStorage C K)
    ⟨Signatures.BQueue.UpdateOp.push, packet⟩

/-- Output plan used by both output ports: pop while the gate is open. -/
def outputPlan {C P K : Nat} {α : Type _} (gateOpen : Bool) :
    Option α ⊕ (storageSignature C P K).Output :=
  if gateOpen then
    Sum.inr popIfNonempty
  else
    Sum.inl none

end CyclicGatedShaperDual

/--
One-input, two-output cyclic gated shaper over the fused dual-counter phase storage.

`C` is the FIFO capacity, `P` the half-cycle length, `K` the queue-view refinement dial
(unused by the step).  The step branches on a single visible bit — is the gate open? —
and the update list is the same on every tick.
-/
def cyclicGatedShaperDual (C P : Nat) (K : Nat := 0) : device 1 2 where
  BranchType := Unit
  ModifType := Empty
  Storage := CyclicGatedShaperDual.storageSignature C P K
  step := fun _inspect _modify input shape =>
    let gateOpen := shape.1
    let plan := CyclicGatedShaperDual.outputPlan (C := C) (P := P) (K := K) gateOpen
    let packet := input.get ⟨0, by omega⟩
    (Vector.ofFn fun _port : Fin 2 => plan,
      [CyclicGatedShaperDual.advancePhase (C := C) (P := P) (K := K),
       CyclicGatedShaperDual.pushInput (C := C) (P := P) (K := K) packet])

end CoreSST.Devices

3 · Per-node exact reachable cells (the ISL-computed domain)

The transition system above is fed to the analysis engine, which computes — per visible node — the exact set of reachable states as a finite union of conjunctive cells. These cells are what the rest of the pipeline runs on: the node names in the graph above (e.g. closed · q≥1) are the values these cells pin at every node, and the elided guard atoms in step 2 are exactly the ones these cells already imply.

How ISL computes this. Each visible node carries a set of states; we represent that set as an ISL (integer set library) Presburger set — a parametric union of convex integer cells over gate, t, q, with C and P kept as symbolic parameters. Each edge becomes an affine ISL map (guard as domain constraints, assignment as the output tuple). Reachability is then computed one strongly-connected component at a time, in topological order: the cycles inside each component (the gate keeps cycling) are collapsed with ISL's exact transitive closure rather than unrolled tick by tick, and the result flows forward to the next component. So the computation finishes in finitely many steps and the result is exact — not an over-approximation (the export records exact = true), parametric in C and P. Because C and P stay symbolic, the cost of this step scales with the size of the visible control graph and the ISL Presburger operations — not with the numeric magnitude of C or P: the same cells come out whether C = 5 or C = 977, which is why this example uses such large sentinels. (Unrolling the counters instead would make the work scale with C·P.) This is an untrusted oracle: the cells it proposes are re-checked for coverage and inductiveness against the typed Lean system.

# one-step relation of an edge (guard G, assignment A), as a parametric ISL map:
#     step(e) := { (x, A(x)) | x ⊨ G }

# REACH — exact reachable set at every node, computed SCC by SCC. This is the
# shared engine: step 5 calls the very same function.
function REACH(system):
    R[n] := system.seed[n]                 # initial sets (∅ where there is none)
    for each SCC comp of system, in topological order:
        # states entering comp: the seed plus flow from already-finished SCCs
        entry := seed landing in comp
        for each edge e: u --> v   with v ∈ comp, u ∉ comp:
            entry := entry ∪ apply(step(e), R[u])

        # collapse every cycle inside comp at once — HERE is the closure:
        loop      := ∪ { step(e) | edge e lies entirely inside comp }
        loop_plus := transitive_closure(loop)   # <<< ISL EXACT transitive closure
        reached   := entry ∪ apply(loop_plus, entry)   # every number of laps, one shot

        for each node v ∈ comp:  R[v] := reached ∩ (configurations at v)
    return R

R := REACH(visible system)     # step 3: seed = the initial config n0; parametric in C, P

Why do this before building the WACS (step 4)? The reachable cells are not cosmetic — they are what makes the delay analysis both small and finite. (i) They prune the WACS to live behaviour: configurations the device can never be in (e.g. a nonempty-queue state with q = 0) are dropped, so the delay automaton has fewer states and transitions. (ii) They discharge guard atoms (the elided ones above), keeping every transition label minimal. (iii) Most importantly, the relational invariants they expose — here q + t ≤ P at closed · q≥1 and q ≤ t+2 at open · q≥1 — bound how large the queue can grow relative to the phase timer. Those bounds are exactly what makes the worst-case delay finite (and tight): without them the cyclic graph would let the accumulated cost appear unbounded.

4 · The WACS delay automaton

The idea is to measure delay by tagging one packet. Starting from any reachable state of step 2, we inject a packet, tag it, and follow it until it is forwarded, counting the ticks. For this example that means adding a single variable, pos — the position of the tagged packet in the queue, numbered from the head (0 = next to leave). The packet is appended at the back, so if q packets are already queued when it arrives, they are all ahead of it and pos = q. Each tick the packets ahead are dequeued and pos drops; when the tagged packet reaches the front and is popped it leaves — and the ticks elapsed are its delay.

Formally this is a weighted affine counter system (WACS): the step-2 system extended with pos and restricted to the reachable states of step 3. It has 8 states over gate, t, q, pos, 31 weighted transitions, 4 roots (where the tagged packet arrives, at cost 0), and 13 exits. Each transition adds its weight to a running cost — here every weight is 1, one device tick — so cost counts the ticks since arrival. An exit fires when the tagged packet is popped, so the cost at that moment is its delay; the worst-case delay is the maximum cost over all root → exit runs (step 5 computes it).

How this connects to the figure of step 2: the WACS is that same system “with a finger on one packet”. Every state is a node of step 2 with the tracked position pos adjoined: the four root states are the four nodes at the instant the tagged packet arrives, and the live tracking states occupy the same grid slots as their step-2 nodes. A tracked packet forces q ≥ 1 (it sits at pos ≤ q-1), so the tracking states over the q=0 nodes are unreachable — every transition into them is infeasible (15 of the 31 transitions and 4 of the 13 exits are such dead cases; they are marked in the tables and omitted from the figure). Every live transition is one device tick (weight 1).

5 · Computing the delay from the WACS

The delay is the longest a tracked packet can sit in the system, i.e. the largest accumulated cost over every run from a root (arrival) to an exit (departure). The graph is cyclic — the gate keeps cycling — so we cannot simply enumerate paths; the worst case is found in closed form with ISL:

Where does cost live? It is simply another variable — a non-negative integer dimension adjoined to every node's set, alongside the device variables and pos. It is not part of the device; it is the observer's tick counter, carried by the very same affine machinery (a root pins cost = 0; each transition's map sets cost' = cost + weight). Reachability over this augmented state is then the same component-by-component closure as step 3:

  1. State-cell graph. Take the live WACS as a graph: nodes are the (state, reachable cell) pairs of step 4, edges are the weighted transitions. Each node carries an ISL set of (device variables, pos, cost) tuples, parametric in C and P.
  2. Seed. Put each feasible root in with cost = 0.
  3. Close component by component. Process the SCCs in topological order, pushing sets along edges and adding each transition's weight to cost. A strongly-connected component (a cycle of states) is not unrolled: its internal weighted relation is collapsed once with ISL's exact transitive closure, which expresses "any number of laps, each adding its ticks" as a single parametric set. The relational reachable invariants from step 3 (e.g. q + t ≤ P) are part of these sets, so the closure stays bounded.
  4. Maximize at the exits. At every reachable finite exit, intersect the node's reachable set with the exit guard and ask ISL for the maximum reachable cost. The overall delay is the maximum of these over all exits. If any infinite exit is reachable, or a maximum is unbounded, the delay is infinite.
# the WACS = the step-2 system + pos, with one extra `cost` dimension; each
# transition's one-step relation (guard G, assignment A, weight w) also bumps cost:
#     step(t) := { ((x, c), (A(x), c + w)) | x ⊨ G }
# and its seed pins every feasible root at cost = 0.

S := REACH(WACS)               # <<< the SAME function as step 3, over (vars, pos, cost)

delay := 0                     # the only extra work: take the largest cost at the exits
for each reachable exit (node n, guard E):
    delay := max(delay, ISL_max(S[n] ∩ E, cost))   # ∞ if unbounded
return delay

For this example the oracle returns: finite, delay = P+1 (with P = 541 in this run, that is 542 ticks). (8 state-cell nodes; 2 exact closure call(s); exact (no precision lost); trusted = false — a proposal Lean re-checks.)

Intuitively this is the right answer: the worst case is a packet that arrives just as the gate closes. It then waits out the entire closed half-cycle (P ticks) before the gate reopens, plus one more tick to be forwarded — a delay of P+1, independent of the capacity C. The whole computation is an untrusted oracle: the value and its supporting reachable sets are handed back to Lean, which certifies the bound against the typed device before CoreSST reports it.

6 · Ongoing and next steps

The example above is a single device, carried through the whole pipeline. Three directions are in progress or planned:

  • Modular state construction. A library of reusable state components, each shipping its three views — the concrete state, the visible projection the control may branch on, and the affine update relations the analysis runs on: bounded FIFO queues, counters, control state, and the combinators that assemble them (product, vector, …). A device is then built from these pieces, and its automaton, reachable sets, and WACS follow from the components' views instead of being hand-derived per device.
  • Other properties and queries. The WACS is a generic weighted automaton, so the same engine answers more than worst-case delay — for instance whether the delay is bounded at all, the maximum queue occupancy a packet sees, or other quantitative queries — each just a different weighting or aggregation over the same construction.
  • Modular (compositional) analysis. Sequential composition of devices does not preserve the structure that makes a single device tractable: the input of a downstream device is the output stream of the upstream one, and a device may branch on that incoming packet — so the two are coupled and cannot be analyzed independently with a free input. The plan is to analyze each device's delay under a constrained input stream (an assumption on its arrivals) and to find a way to propagate those stream constraints along the pipeline: the constraint a device guarantees on its output stream becomes the assumption the next device is analyzed under.
